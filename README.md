# Instructions for candidates

This is the Python version of the Payment Gateway challenge. If you haven't already read the [README.md](https://github.com/cko-recruitment) in the root of this organisation, please do so now. 

## Template structure
```
├── .editorconfig - don't change this. It ensures a consistent set of rules for submissions when reformatting code
├── .env.example
├── .python-version - Python version used by Pyenv (https://github.com/pyenv/pyenv).
├── Makefile - Makefile with commands such as install, run and test
├── docker-compose.yml - configures the bank simulator
├── pyproject.toml - project metadata, build system and dependencies
├── poetry.lock - Poetry lock file
├── main.py - app's entrypoint
├── payment_gateway_api/ - skeleton FastAPI API
├── imposters/ - contains the bank simulator configuration. Don't change this
└── tests/ - folder for tests
```

Feel free to change the structure of the solution, use a different test library etc.

## Design notes

`payment_gateway_api/` is organized into `models/` (request validation and
response shapes), `clients/` (bank adapters), `routing/` (bank-selection policy),
`repositories/` (in-memory storage), `services/` (orchestration), and `observability.py` (request-correlated logging). The top-level scaffolding
(`Makefile`, `.env.example`, `docker-compose.yml`, `imposters/`, `main.py`)
is retained from the challenge template.

### Multi-bank routing

`PaymentService` depends on `BankRouter`, not on a concrete bank client.
Each bank implements the same `BankClient` contract.

The routing policy is deliberately simple and does not depend on currency:

- a stable hash of the card number selects one configured bank;
- the same card therefore maps consistently to the same bank;
- exactly one bank receives an authorization request;
- an unavailable selected bank is never treated as a reason to send the same payment to another bank.

The default configuration contains three banks:

- `primary`: the supplied bank simulator on `localhost:8080`;
- `mock`: a local mock bank that immediately returns `503`/unavailable;
- `simulated`: another local bank double that immediately returns `503`/unavailable because no simulator is supplied for it.

This demonstrates multi-bank routing without inventing a currency-based rule or
modifying the supplied simulator.

The bank client protocol, factory, and router keep bank-specific details behind
an adapter boundary. This is intentional: adding another bank that follows the
same contract should require a new configuration entry, rather than changes to
the payment service or API. A bank with a different protocol can be added with
its own adapter implementing the shared client contract.

### Bank failures

There is intentionally no retry library and no circuit breaker. A timeout,
connection failure, or upstream `5xx` is surfaced as bank unavailable immediately.
The selected bank is never replaced by another bank for the same authorization.

### Logging and observability

The application uses standard Python logging and records:

- request start/completion information including a request ID, payment ID,
  HTTP status and duration;
- payment processing start/completion;
- which bank was selected and the routing rule used;
- bank authorization start/completion;
- bank availability failures;
- validation and unexpected errors.

No full PAN or CVV is logged. Where card identification is useful, only the
last four digits are used. Upstream response bodies are not logged.

The request ID is accepted from `X-Request-ID` or generated by the API and is
returned in the response header. A payment ID is generated before the bank
call, so the same payment can be followed through service, routing, bank, and
completion logs. For example:

```
request_id=req-123 payment_id=pay-456 payment_processing_started
request_id=req-123 payment_id=pay-456 bank_selected bank_id=primary
request_id=req-123 payment_id=pay-456 bank_authorization_completed authorized=True
request_id=req-123 payment_id=pay-456 payment_processing_completed status=Authorized
```

These are key-value log messages suitable for collection by a container
runtime or log aggregation system. The next production step would be to emit
the same fields as JSON and add OpenTelemetry trace/span propagation between
the API and acquiring banks.

### Metrics and health checks

The API exposes Prometheus metrics at `/metrics`. The application records HTTP
request totals and duration, bank authorization totals and duration, completed
payments by currency and status, routing distribution, validation failures,
and idempotency replays. Bank authorization outcomes include `authorized`,
`declined`, `unavailable`, and `rejected`.

`/health` is a liveness check and returns `200` while the process is running.
`/ready` validates that the configured bank clients and routing IDs can be
constructed and returns `503` for invalid application configuration. It does
not call the banks, so a temporary outage of one bank does not make the whole
gateway unready.

Prometheus is integrated as the metrics exposition format for this exercise.
The next observability step for a deployed environment would be to configure
Prometheus to scrape `/metrics`, then connect Grafana dashboards and alerts to
the collected request, bank, routing, payment, validation, and idempotency
metrics.

### Deliberately left out

There is no real database. Storage is an in-memory repository, as permitted by
the challenge. Idempotency-key handling is included in the service layer so
repeated requests with the same key do not authorize the payment twice. The
idempotency records and per-key locks are deliberately simple in-memory
structures for testing the behavior without a real database. A production
implementation would use shared durable storage so idempotency works across
multiple application processes or instances.

### Running it

```
make install
docker-compose up -d   # bank simulator on :8080
make run                # http://localhost:8000
```

### Testing it

```
make test
docker-compose up -d && poetry run pytest tests/integration/test_live_bank_simulator.py
```

The default suite mocks the bank at the `httpx` transport layer. The one
exception is `test_live_bank_simulator.py`, which talks to the real
simulator using the documented card-ending-digit routing from
`imposters/bank_simulator.ejs`; it's skipped automatically if the
simulator isn't running.

### Note on `.python-version`

Bumped from the template's `3.8.10` (end-of-life since October 2024) to
`3.12.3`, with `pyproject.toml`'s `python` constraint updated to match --
the only deviation from the shipped scaffolding, and made for a
version-currency reason rather than a structural one.
